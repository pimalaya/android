# Step 3: the store on the platform's SQLite

The app opens every database it owns, the pimdir store and the contacts database (`CardStore`), on the platform's `android.database.sqlite`; requery's bundled SQLite (cairn/log/2026-10-10-bundled-sqlite.md) is gone. Steps 4 (the index) and 5 (the lists) remain, and the change stays in flight (cairn/changes/archive/platform-sqlite/tasks.md).

Capabilities moved: offline-store (folded at the change's landing, not yet: cairn/changes/archive/platform-sqlite/delta.md).

- **The swap**: the `io.requery.android.database.sqlite` imports of 15 main classes and 19 test sources back to `android.database.sqlite`; requery out of android/app/build.gradle.kts and its JitPack repository out of android/settings.gradle.kts. It had no keep rule (android/app/proguard-rules.pro, android/client/consumer-rules.pro). The release classpath holds neither requery nor androidx.sqlite nor the Kotlin standard library they brought. The one call requery had and the platform lacks below API 35 was `beginTransactionDeferred`, for a read binding lists through `temp.param` in a transaction of its own: it is `beginTransactionNonExclusive` now, both holding the writer's connection, the only one that writes, for the read's length. No custom SQL function was registered from Java, no `OpenParams` used, no update hook, no extension.
- **Why requery came in, each reason answered** (2026-10-10): `STRICT`, `RETURNING`, upserts, `UPDATE ... FROM` and `json_each` are out of the statements since step 2b (the floor guard); JSON is out of the canonical schema since storage-draft-07; FTS5 is not used (the index, step 4, is FTS4); no function is registered from Java (the platform's `setCustomScalarFunction` is API 30 and string-only); `PoolProbe` sat in requery's package to read its pool, and the test now counts the connections opened through the test binding (below).
- **The JVM tests run the platform's classes on Android 8.0's SQLite.** The store calls Robolectric's copy of the platform's `SQLiteOpenHelper`, `SQLiteDatabase`, connection pool, sessions and cursors (SDK 36), whose natives `SQLiteConnection` and `CursorWindow` are shadowed for every test (android/app/src/test/resources/robolectric.properties) by `ShadowHostSqliteConnection` and `ShadowHostCursorWindow` (android/app/src/test/java/org/pimalaya/sqlite/). They hand each call to `HostSqlite`, whose natives flake.nix `sqliteHost` builds: requery's copy of the AOSP JNI (SQLiteConnection, CursorWindow, SQLiteGlobal, unchanged) over the 3.18.2 sources with the floor's own flags, ICU included (`sqliteFloorFlags`, shared with the floor guard's build), linked `-Bsymbolic` and `--no-undefined`, its natives registered on the test class alone. The shadows keep Android 8.0's behaviour where the platform's natives grew since: the platform's open flags turned into SQLite's as AOSP does, a pragma run by `execSQL` answering a row refused, `nativeUpdatesTempOnly` false, Java-registered functions refused; the three natives API 35 added (`nativeLastInsertRowId`, `nativeChanges`, `nativeTotalChanges`) written in the host JNI. `HostSqliteTest` checks `sqlite_version()` 3.18.2, FTS4 in, JSON, FTS5 and `STRICT` refused, `trusted_schema` absent; without the shadows it answers Robolectric's 3.44.3. `PIMALAYA_SQLITE_HOST` is the only variable left; `-Ppimalaya.sqlite=bundled` and the 3.49 host build went with requery.
- **Write-ahead logging stays turned on in onOpen.** On the platform too, logging turned on in onConfigure opens a reader for the helper's version read before onCreate (seen as `pimdir.db (2)` in onCreate), the reader that cached an empty schema in 2a. API 36's pool closes that reader again before the store is handed out, and reopens the writer itself when logging turns on, so `openingAFreshStoreOpensNoReaderBeforeItsSchema` now counts the connections opened beside another to the same file (`ShadowHostSqliteConnection.openedBeside`), not the ones open after: it fails with logging in onConfigure, and passes as the store opens.
- **`synchronous = FULL` on the writer** (STORAGE §4.1), set after logging is on, turning it on having set the platform's default for logging (`db_wal_sync_mode`, FULL on AOSP, NORMAL on some builds). SQLite refuses the change inside a transaction and applies it as it compiles the pragma, which the platform does on the writer for any statement but a `SELECT` (SQLiteProgram), so onOpen compiles `SYNCHRONOUS_FULL` without running it, which would open a reader. `theWriterSyncsEveryCommit` sets the platform's default to NORMAL and reads FULL on the writer, on a fresh store and on one opened again; it failed first (NORMAL) without the pragma. Readers keep the platform's default, which STORAGE §4.1 asks per connection: they commit nothing, so nothing a power loss could undo rests on them.
- **`secure_delete` and `trusted_schema`**: the platform compiles `SQLITE_SECURE_DELETE`, so `secure_delete` is on by default and the store's `SECURE_DELETE_ON` restates it; `TRUSTED_SCHEMA_OFF` runs only on SQLite 3.31 and later (Android 12), read off `sqlite_version()` in the writer's transaction. `SQLITE_DBCONFIG_DEFENSIVE` (3.26) is a C call the platform's Java reaches at no API level: not set (STORAGE §18 asks it as a SHOULD, for a store from elsewhere).
- **The store logs its SQLite at open**: `store on sqlite 3.18.2` (tag `pimalaya`), from the shape's new `SQLITE_VERSION` statement (`theStoreLogsItsSqliteAtOpen`).
- **A store step 2b wrote opens unchanged**: `aStoreTheCanonicalTextWroteOpensAsTheSameStore` runs on 3.18.2 through the platform's classes; `a_store_a_newer_sqlite_wrote_opens_on_the_floor` (rust/src/ffi/offline.rs) writes the canonical store under write-ahead logging with rusqlite's bundled SQLite and reads, writes and checks it with the floor's 3.18.2 shell, as the platform will read a store requery's 3.49 wrote; a `STRICT` table in it fails the test. A store of the app before step 2, whose `STRICT` tables 3.18 cannot parse, is refused as `store-foreign` and left byte for byte (`aStoreWithStrictTablesIsRefusedAndLeftAsItWas`).
- **Size** (release, R8, unsigned, the same libpimalaya.so in both): arm64-v8a 12,379,632 to 10,488,378 bytes (-1.89 MB), armeabi-v7a 8,896,092 to 7,612,828 (-1.28 MB), x86_64 13,663,362 to 11,773,223 (-1.89 MB), x86 13,567,716 to 11,636,432 (-1.93 MB), universal 46,251,574 to 39,380,481 (-6.87 MB): libsqlite3x.so (1.84 MB on arm64-v8a) gone, classes.dex 968,664 to 882,592 bytes.

Verified on 2026-11-01: `gradle :app:assembleDebug :app:testDebugUnitTest :client:testDebugUnitTest :app:assembleRelease` green (837 app tests, 14 client) on 3.18.2 through the platform's classes; `cargo test` 582 passed, the floor guard included; `cargo fmt` and `cargo clippy --all-targets -- -D warnings` clean; cairn/verify.sh conformant; `gradle :app:lintDebug` reports no NewApi finding in the store's code.
