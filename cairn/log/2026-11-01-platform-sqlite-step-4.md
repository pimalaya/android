# Step 4: the search index on the platform's SQLite

The app keeps pimdir SEARCH.md's index, index.db beside the store, in a shape of its own over FTS4, refreshes it with io-pimdir's I/O-free refresh, and its mail search reads it, bodies included. Step 5 (the lists) remains, and the change stays in flight (cairn/changes/platform-sqlite/tasks.md).

Capabilities moved: offline-store and mail (folded at the change's landing, not yet: cairn/changes/platform-sqlite/delta.md).

- **The shape, `pimalaya-android`** (SEARCH §2, §12): rust/pimdir/migrations/search/0001_init.sql forks the canonical schema for SQLite 3.18, `STRICT` as one `CHECK (typeof(...))` per column, and `object_text` and `summary_text` as ordinary FTS4 tables, `tokenize=unicode61 "remove_diacritics=0"`, `prefix="2,3"`, keyed by docid on `object.id` and `placement.id`, the text folded by io-pimdir before it reaches them (SEARCH §5). The user chose ordinary over contentless with a live-row table (2026-11-01): FTS4 deletes from no contentless table. `index_meta.shape` is `pimalaya-android`, `tokenizer` the FTS4 argument, `format_version` `search-draft-08`. rust/pimdir/queries/search/ forks the canonical statements 3.18 refuses, each naming the digest of the text it forks (`init_index_meta`, `insert_object`, `upsert_placement`, `upsert_message`, `upsert_thread`, `delete_placement`, `prune_messages`, and `match_objects` and `match_summaries` without `bm25`); `match_objects_ranked` is not served, the shape ranking nothing. rust/pimdir/queries/index/ holds the app's own: the writes keyed on a body's hash or a placement's key rather than on an id a statement returns, so a run's writes go out in one round, the summary reads keyed on `(collection, seq)`, the schema checks, the attach and a run's transaction. build.rs embeds them; rust/src/search/shape.rs serves them by name, the store's statements beside them for the fold's reads.
- **Held, built, rebuilt or refused** (rust/src/search/held.rs, SEARCH §2): an index with no `index_meta`, of another shape or of a later version is refused and left byte for byte; one of this shape at an earlier draft, at another schema version, under another tokenizer, whose schema text differs object by object, built from another store or copy, or folded past the store's last stamp, is deleted and built again.
- **The refresh** (rust/src/search/refresh.rs): io-pimdir's `PimdirIndexRefresh` driven over the shape, each yield one round of SQL steps to Java's owner, the bodies read off the blob directory in Rust and checked against their name (a link, a missing body or one failing its name read as missing, SEARCH §4), each `Writes` mapped to the shape's statements in order. Java's `PimdirIndexDb` (android/app/src/main/java/org/pimalaya/pimdir/) is the only writer of index.db, under the store's new index lock (`Locks.index`): it holds the file, one handle with the store attached as `store` (so rollback-journal mode, the attach costing the handle write-ahead logging), and runs the steps it is sent (`PimdirIndex.Steps.serve`), never SQL of its own. A run folds at most 200 rows of the feed and commits; a query waits at most one run.
- **A run is a deferred transaction the bridge opens** (`BEGIN_RUN` is `SAVEPOINT index_run`, `COMMIT_RUN` its `RELEASE`), never one of the platform's: below API 35 those are immediate or exclusive and take the write lock of every attached database, which would hold the store's writer off for a whole run. `a_run_holds_the_store_writer_off_never` shows it on the 3.18.2 build: a store write during a deferred run goes through, during an immediate one it fails `database is locked`. A run that fails closes the handle, which rolls it back; the next run opens it again. Every use of the handle goes through `PimdirIndexDb.run`, synchronized, so the one connection is never shared mid-run.
- **Wired**: `App.pimdir()` starts the index and asks a refresh at start (`PimdirDb.startIndex().refreshSoon()`); `Stager` asks one after each engine write batch it commits (SEARCH §4), and `Locks.releaseSync` after each sync, a refresh asked while one runs coalescing into one more on the index's own thread. A store a test opens starts no index.
- **The compile** (rust/src/search/compile.rs): a `PimdirQuery`, parsed by io-pimdir with its limits and refusals, compiled to the shape's SQL as io-pimdir's canonical compile does, one `MATCH` per text term read into `temp.term_match` before the query and the boolean logic in SQL, so FTS4's basic query syntax is never asked for more than one phrase. A text term is folded, every ASCII character but a letter or a digit written as a space (`unicode61` splits on them alike, and none is left as FTS4 syntax), and quoted, its last token starred for a prefix; a field term filters by the `MATCH`'s left operand (`object_text."from" MATCH`), FTS4's `column:` reading one token and never a phrase. `has:phone` and its siblings test an `EXISTS` rather than a row value `IN`, which 3.18 refuses over `holding`'s `CASE`. Ordered by `date` (the default) or `name`; no relevance.
- **The answer** (rust/src/search/find.rs): every hit as `(account, seq)`, or a page described with its placements, kind, title and a snippet cut from the body in Rust around a word of the query (io-pimdir's canonical query client's cut), never FTS4's `snippet()`; a refusal answers `{"refused": {code, message, start, end, expected, fields}}`. Exports `Native.pimdirIndexHeld`, `pimdirIndexInit`, `pimdirIndexRefresh`, `pimdirIndexHits`, `pimdirIndexSearch` and `pimdirIndexStatement`, through `:client`'s `PimdirIndex`, its `Steps.serve` kept by android/client/consumer-rules.pro.
- **The mail search**: `MailStore.query` asks the index for the hits of the words (`SEARCH_MAIL_INDEXED`, rust/pimdir/queries/app/), and the list pages, counts and groups by day what `search_mail` matches (sender and subject, as before) or the index hits, by seq through `temp.param`; so a word inside another, mail not indexed yet, or a query the index refuses still finds what it found before. A refused query says why on the search field (`ListHeader.searchError`). Contacts and calendar have no search field: none added.
- **io-pimdir with `search`**: the bridge builds io-pimdir with its `search` feature (the coroutine, the fold, the parser, extraction), and ical-rs moves from caa1422 to 99b9273, the revision io-pimdir 09d2d1c's occurrences need.

## Vectors

io-pimdir's vendored search vectors (spec/vectors/search/ at 09d2d1c, store.json built through io-pimdir's owner as its own suite does) run against the shape on SQLite 3.18.2, loaded by `dlopen` from the floor's build (rust/src/search/floor.rs, `RTLD_DEEPBIND` beside the bundled SQLite of the test binary): `the_search_vectors_answer_on_the_floor` answers 166 of 168 cases and every occurrence window, refusals compared by code and span, hits as sets or in order as the case says. Two do not bind the shape: `roadmap` sorted by relevance (the shape refuses the order, SEARCH §8.2) and the one threaded listing (`account:home (stand-up or roadmap)`), which the app does not offer. Not compared: the coverage a case states (`horizon_left`, `cut`, `temporal`, the bodiless counts), which the app's answer does not carry.

## Weight

On the host 3.18.2, a thousand synthetic messages of about 2.1 KB of body text each, words drawn from a vocabulary of 5,000 (`index_weight_per_message`, run by hand): index.db weighs 9.0 MB, 9.0 KB per message, of which the FTS4 copy of the text holds about 2.2 KB; a contentless table would save that share, about a quarter. Real mail repeats its words more, so this is an upper side; a device measure after a large first sync is owed.

## Device check (2026-11-01)

OnePlus 5, Android 15, installed over the step 3 store (the Fastmail test account). index.db created beside pimdir.db in rollback-journal mode (no `-wal`), `index_meta` at `search-draft-08`, shape `pimalaya-android`, 21 bodies and 14 summaries indexed after start. A word found only in a body (`platform`) found its message; an unclosed quote showed its refusal as the field's error; a search typed during a mail sync answered (four hits for `check`) with no `database is locked`, no `SQLiteException`, no `search index` warning.

Found at start-up, not the index's doing: `SQLiteConnection: Could not change the database journal mode of pimdir.db from 'wal' to 'TRUNCATE' because the database is locked`. `PimdirDb` turns write-ahead logging on in `onOpen` (the 2a fix keeping a reader from caching an empty schema), so the platform first opens the writer with its default journal mode and tries `TRUNCATE` on an existing WAL store; where nothing holds it, the store flips to TRUNCATE and back on every open, which STORAGE §8 forbids (the journal mode is set at creation). It shows now because the index's handle holds the attached store at start. Fixed with the re-pin to io-pimdir fd0c060.

## The journal mode at start-up (2026-11-01)

The fix landed with the re-pin to io-pimdir fd0c060 (cairn/log/2026-11-01-the-shape-follows-storage-draft-08.md). `PimdirDb`'s constructor now calls `setWriteAheadLoggingEnabled` when pimdir.db exists and is not empty, so the platform opens an existing store with `ENABLE_WRITE_AHEAD_LOGGING` and configures every connection in WAL from its first statement: it asks no other journal mode of the file (STORAGE §8). A fresh store keeps the 2a path, logging turned on in `onOpen` after `onCreate`, so the helper's version read still finds no reader before the tables exist (`openingAFreshStoreOpensNoReaderBeforeItsSchema` unchanged and green). `onOpen`'s `enableWriteAheadLogging` is a no-op on a store opened in WAL.

- Test: `PimdirDbTest.anExistingStoreOpensInWriteAheadLoggingAlone` closes the store setUp created, opens it again with a writer and a reader, and asserts every `PRAGMA journal_mode=…` the platform ran on a connection to pimdir.db asked WAL and that the file answers `wal`. The host test shadow (android/app/src/test/java/org/pimalaya/sqlite/ShadowHostSqliteConnection.java) now records the mode of each such statement a connection prepares (`journalModesSet`). Failing first against the constructor without the flag: `expected:<[WAL]> but was:<[MEMORY]>`, the platform setting its default mode (MEMORY under Robolectric, TRUNCATE on the device) on the existing WAL store, the path the device log showed.
- Not checked on a device yet: the start-up line should be gone, and pimdir.db keep its `-wal` beside it across starts.
