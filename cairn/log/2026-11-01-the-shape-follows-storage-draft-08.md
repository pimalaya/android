# Step 2a: draft-08 rules on requery, io-pimdir's canonical text

The pin moved to io-pimdir bff5737 (storage-draft-08, sync-draft-07, search-draft-08), and the app keeps running io-pimdir's canonical SQL on requery, served over JNI. Step 2b, the 3.18 shape, is not started. The change stays in flight (cairn/changes/the-shape-follows-storage-draft-08/tasks.md says what is left).

- **The bridge** (rust/): the 12 compile errors ported (PimdirLoadSelection and its `lastPage` selection, `WantsVerify`, `Written`, `Overrule`, `Edit { if_match, overrule }`, `SetFlags { add, remove }`, `PimdirRemoteSnapshot { narrowed, enumerated }`, PimdirMutateReport, the task summary's `created` and `contacts`, BLAKE3). An upgrade settles a divergence by its collection's sync options (`PimdirUpgradeOptions::from`, `Native.offlineUpgrade` taking `content`). The reports carry `overruled`, `parked` and `unreadable`. New pure exports: `pimdirHash` and `pimdirHashFile` (BLAKE3), `pimdirIdentity` (the versions a store is created and opened at), `pimdirCheck` (STORAGE §6's open refusals, decided in offline/store.rs over facts Java reads read-only) and `pimdirAction` (a queue row read strictly by its payload schema, io-pimdir's payloads.json run in `cargo test`).
- **A pending create lands on its arrival again** (offline-store): the engine at sync-draft-07 tells a listed message reusing a create's `Message-ID` by its subject, date and sender (SYNC §6), and the load handed it the date alone, so a sent copy or a moved message never landed and was pushed a second time. A load now carries the three (`subject` and `sender` beside `date`), never written back.
- **The Java owner**: PimdirDb creates the store at draft-08 and reconciles nothing (its reconciliation, backfills and role repair deleted); PimdirBlobs files one shard level under BLAKE3 names, checks a name before a path, writes by hard link and never replaces, follows no link, verifies a body before serving or linking it and moves one failing into quarantine/; flags, reply ids and categories are rows; every list parameter goes through `temp.param` on one pinned connection; `verify` and `Written` are answered and the `overrule` op keeps the bodies it does not adopt as `dup:` retained items; `sync_version` is written by the first engine write.
- **Connectors**: flag pushes are the engine's two deltas on every mail backend; IMAP, JMAP, Graph band pages and Gmail state `narrowed` where the download window filters a round, IMAP handing `UID SEARCH ALL` on its last page; a CalDAV or CardDAV create is pushed under its identity with `esc:` stripped.
- **Start-up blocked on a store of another draft**: App checks the store once before anything opens it; MainActivity hands over to StoreRefusedActivity (reinstall), and the background job, the sync adapters and the time-zone receiver do nothing.
- **Behaviour the canonical text and the engine moved**: an empty listing parks its round rather than retiring every member (SYNC §5, §8), so a calendar or book the server emptied keeps its items until a listing names members; an attachment saved into a device folder no longer reads as held on its message (`list_attachments` reads within the message's account, STORAGE §9.2); the calendar mirror's row fingerprint stays the app's own SHA-256, never a store name.

Capabilities moved: offline-store (folded at the change's landing, not yet).

## Second pass (2026-11-01): what the first left, and what the device found

- **Bodies stored on a device again** (found by the device check on a OnePlus 5, Android 15, debug build of 3693cff): SELinux denies `link` to an untrusted app on its own data files, so every no-replace write by hard link failed (`AccessDeniedException` from `Files.createLink` in PimdirBlobs.commit and adopt) and no mail body was stored, while the host, allowing hard links, passed every test. The write now renames the temporary with `renameat2(RENAME_NOREPLACE)`, a raw system call in the bridge (`Native.pimdirRename`, offline/blobs.rs; bionic exports `renameat2` from API 30 alone), a name held keeping its file; a kernel or file system without it falls back to a check-then-rename whose race only ever replaces a file by the same bytes. `adopt` renames its source the same way, copying where it cannot (another file system); the quarantine move was already a rename. A JVM test scans the owner's sources for `createLink(`.
- **Strict payloads** (STORAGE §15.3, Annex B.2): the app's `submit` is the standard's, built in Rust from the message (`Native.pimdirSubmit`: `source` `server`, `from`, `rcpts` from `To`, `Cc` and `Bcc`, `subject`); the outbox's `Message-ID`, subject and date are derived from the message by Annex A (cached by body), never carried in the payload. `PimdirQueue.enqueue` refuses a malformed payload before writing anything; the drain reads each row through `Native.pimdirAction`, parking a malformed one whole (a row of the first pass's payload included) and skipping one stating a later version, left pending and untouched as io-pimdir 77c8e4c's pending reads skip it; SMTP and JMAP send with the payload's envelope.
- **`bindings.shared_object`** (STORAGE §5, SYNC §9): written with every upsert, moved only by one carrying a body the item settled on, pinned like the base (its refcount, `RECOMPUTE_REFCOUNTS`, an item's removal, the cross-linked release).
- **The cross-source merge**: an upsert of a mutable kind is absorbed by io-pimdir's own `PimdirHub` over the item and its bindings (`Native.pimdirMerge`, offline/merge.rs), so two sources changing one item diverge: the item keeps its body, records the incoming one in `conflict_object`, stands conflicted for every source, and `Written.conflicted` names the handle. Before, the last source listed overwrote the other's edit.
- **Parked rounds asked about**: `SyncReport` carries the parked round's `absent` and `bound`, ParkedRounds keeps them for the process, and a pass ending with one shows a dialog naming each collection and its counts, Remove running the drawer's sync with `accept_absences` for those collections, Keep leaving them parked until what a round finds changes. - **Narrowed rounds enumerate** on JMAP (`Email/query` filtered by the mailbox alone, ids only: one query per page of the session's page size, 256 at most), Graph (`/messages?$select=id`: one request per 1,000 ids) and Gmail (`messages.list` by the label with no query: one request per 500 ids), on the last page of a round a date filter narrowed. A round of a 10,000-message mailbox thus ends with 10 to 40 more requests; IMAP's `UID SEARCH ALL` stays one.
- **"no such table: collections" on a first launch**: not introduced by 3693cff's refusal check, which returns before opening anything when no store exists. Write-ahead logging was turned on in onConfigure (since before 3693cff), so the helper's own version read, a read-only statement, ran on a pooled reader before onCreate, which cached the empty schema and failed its first statements once each before SQLite reloaded it; 3693cff's pragmas, set after logging was on, also ran on a reader and never reached the writer. Logging is now turned on in onOpen, after onCreate, and `secure_delete` and `trusted_schema` are set on the writer inside a transaction; `synchronous = FULL` is dropped, requery resetting every connection to NORMAL under logging.

## Step 2b (2026-11-01): the app's own statements, on SQLite 3.18

The store's statements are the app's own text, the `pimalaya-android` shape, which Android 8.0's SQLite 3.18 runs; the store stays on requery (3.49) until platform-sqlite step 3. Only SQL moved: the rules are 2a's.

- **One on-disk format, no shape recorded** (pimdir STORAGE §4.1, §4.4, §6; pimdir cairn/log/2026-10-31-format-identity-and-versions.md, D3): draft-08 dropped storage-draft-07's `store_meta.shape` and its refusal, made 0001_init.sql load on 3.18 (`CHECK (typeof(…))` in place of `STRICT`), holds pimdir.db to the canonical schema alone, and leaves a statement's text free so long as its name, parameters, columns and effect are kept. So the app forks the statements and never the schema: `Native.pimdirMigrations` still serves io-pimdir's, no `store_meta.shape` is written, and a store 2a wrote is the same store, which opens (`aStoreTheCanonicalTextWroteOpensAsTheSameStore`). The start-up block still refuses another draft, another schema or an unreadable file. The app states its conformance as `storage-draft-08 owner, sync-draft-07 engine` (§17), its statements its own.
- **The shape** (rust/pimdir/queries/, embedded by rust/build.rs, served by rust/src/offline/shape.rs as `Native.pimdirSql`): 39 canonical statements rewritten under their own names, each naming the SHA-256 of the canonical text it forks, so a pin moving that text fails `cargo test` until the fork is read again. `RETURNING` (11) becomes the write and a read of what it wrote (`bump_next_seq`, `bump_generation`) or a read of what it deletes then the delete under the same predicate (`cancel_action`, `claim_action`, `purge_item`, `delete_unbound_item`, `purge_retained_before`, `collect_before`, `release_before`, `remove_reference`); an upsert's `DO UPDATE` (15) an update of the row then its insert where none is there; `DO NOTHING` (11) one insert of what is not held (`NOT EXISTS`, the rows `DISTINCT`), never `INSERT OR IGNORE`, which would swallow a `CHECK` the canonical text raises on; `add_reference` the three; `UPDATE ... FROM` (2) correlated reads, `recompute_refcounts` a sum of six counts each seeking its pointer's index so it stays linear; `create_param` without `STRICT`, its `value` untyped so no affinity turns '007' into 7.
- **Several statements, one name, one transaction**: `PimdirSql.bind` answers a name running several as `Bound.steps`, which only `PimdirDb.exec`, `changed`, `query` and `read` run, in order, in the caller's transaction or one of their own (`beginTransaction`, which takes the writer at once), a read's rows copied and a write's changes summed; `Bound.sql` is null for such a name, so a caller running it otherwise fails at once rather than running half. Where 3.18 splits one statement into two, the two run under the store's one writer from the first, so nothing comes between them: the same atomicity the one statement had.
- **Java's SQL moved in**: 77 statements of the app's own (rust/pimdir/queries/app/) in place of every SQL string PimdirStorage, PimdirItems, PimdirCollections, PimdirQueue, PimdirDb, PimdirContacts, MailStore, Outbox, EventStore and TaskStore wrote (`json_each` in 5 statements, `ON CONFLICT ... DO UPDATE` 3, `DO NOTHING` 4, the flags and base flags fragments Java spliced in, the `SELECT *` copies of a summary), and canonical statements wherever one had the effect (`adjust_refcount`, `list_garbage_objects`, `delete_garbage_objects`, `delete_binding`, `retain_item`, `insert_item`, `upsert_checkpoint`, `link_for_handle`, `handle_for_link`, `load_kind`, `set_sort_key`, `revive_item`, `delete_collection`, `set_collection_name`). MailStore's wrappers around the canonical mail reads (a count, per-day counts, a page past an offset, the hidden sent copies, the counts' empty summary) are five reads over another (`:inner`, `PimdirSql.wrap`), the hidden pairs bound through `temp.param` rather than `json_each`. The start-up check reads a foreign `store_meta` row whole and hands every column by name to the bridge, which reads the ones it knows (MetaFacts by column name). Java now holds no SQL of the store; CardStore keeps its own over cards.db.
- **The floor at run time**: flake.nix builds requery's JNI binding over the 3.18.2 sources with Android 8.0's flags (`sqliteHostFloor`, no JSON, no FTS5), and the JVM tests load it by default (`PIMALAYA_SQLITE_HOST_FLOOR`), `-Ppimalaya.sqlite=bundled` loading the 3.49 one as before.
